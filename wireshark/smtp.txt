Now SMTP stands for simple mail transfer protocol. It is a standard protocol that defines how mail transfer agents exchange electronic mail across TCP/IP networks formally specified in RFC 5321.
At its core, SMTP operates at the application layer, layer seven of the OSI model. It runs over TCP, which means every message exchange is reliable and connection oriented before a single command is sent.
SMTP is a push protocol. The sender initiates the transfer. This distinguishes it from protocols like POP3 and IMAP where the client pulls messages from a server.
Communication happens through a simple ASCII text based command and response model.
Every command the client sends and every reply the server sends is plain human readable text.
This is precisely why Wireshark can display an SMTP session so clearly.
Finally, SMTP operates on three standardized ports. Port 25 is used for mail transfer between servers.
Port 587 is the submission port used by mail clients to submit outgoing mail.
Port 465 is SMTPS, SMTP over an implicit TLS connection.
Before we analyze packets, it is important to understand the path an email travels from composition to delivery.
Four distinct agents are involved. The first is mail user agent or MUA.
It is the email client that user interacts with directly.
Outlook, Thunderbird, or Gmail, for example.
It is where the message is composed and sent.
The second is the mail submission agent
or MSA.
When the user clicks send, the MUA hands the message to the MSA over port 587 with authentication.
The MSA is the first server in the chain.
The third is the mail transfer agent or MTA. This is responsible for routing the message across the internet from one server to another.
MTA to MTA communication happens over port 25.
There may be multiple MTAs involved depending on the route the message takes.
The fourth is the mail delivery agent or MDA.
This handles the final step, placing the message into the recipient's mailbox.
The recipient then retrieves that message using IMAP or POP3 through their own mail user agent.
So, the complete flow is MUA to MSA over port 587 MSA to MTA over port 25 MTA to MTA over port 25 across the internet, and finally MTA to MDA for local delivery. The recipient's MUA then fetches the messages via IMAP or POP3.
This is the infrastructure through which every email you have ever sent has traveled. In our Wireshark capture we are observing the MTA to MTA segment of this flow, port 25 server to server in plain view.
With the transmission flow understood, let us now walk through the SMTP session life cycle, the precise sequence of commands and responses that occur once a TCP connection is established.
The server always speaks first.
Immediately after the TCP connection is made, the server sends a 220 greeting announcing that ready to receive commands.
The client then sends EHLO identifying itself by its domain name. This is not merely a greeting, it is a request for the server to list its supported extensions.
The server responds with 250 followed by a list of its capabilities.
These may include auth for authentication, size to advertise the maximum accepted message size, and start TLS to indicate support for encrypted communication.
Next, the client sends mail from supplying the envelope sender address in angle brackets.
This is the address the server will use for bounce notifications and error reporting.
The server replies 250 OK confirming the sender is accepted.
The client then sends RCPT to specifying the intended recipient.
If there are multiple recipients, the command is repeated once for each address.
The server replies 250 OK for each valid recipient.
At this point, the envelope is complete.
The server knows who the message is from and who it is going to. The session is now ready to receive the message itself, which we'll cover in the next segment.
Continuing from where we left off, once the envelope is established, the client sends the data command signaling that it is ready to transmit the message content.
The server responds with 354 instructing the client to proceed indicating that the message must be terminated with a carriage return line feed period carriage return line feed which is written as crlf.crlf.
This sequence is the agreed signal that the message is complete.
The client then transmits the full IMF payload. This is the internet message format content as defined in RFC 5322 structured headers first followed by a blank line followed by the message body.
Everything between the 354 response and the terminating period is the actual email.
Once that terminating sequence is received the server replies 250 OK confirming the message has been accepted and queued for delivery.
The client then sends quit formally closing the session.
The server replies 221 bye and TCP connection teardown follows the standard four-way FIN sequence that closes the connection at the transport layer.
That completes the full SMTP session

Every step is deterministic text-based and fully visible in a Wireshark TCP stream capture.
Let us now examine each SMTP client command in detail.
The first is EHLO or it's older counterpart HELO.
This is the opening command that the client sends to identify itself to the server.
EHLO goes further. It also requests a list of the extensions that the server supports.
In modern SMTP EHLO is always used.
The second is MAIL FROM.
This declares the envelope sender address and formally initiates the mail transaction.
It is important to note that this address belongs to the SMTP envelope.
It is used for error reporting and bounce handling and is independent of the from header that the recipient sees in their mail client.
The third is RCPT2. This specifies the envelope recipient. If the message is intended for multiple recipients, this command is issued once for each address.
Each instance receives its own server response. The fourth is data.
This single command signals that the client is ready to transmit the message body. Everything that follows under the terminating period is treated by the server as the message content in RFC 5322 format.
These four commands in this order form the complete client-side logic of every SMTP transaction.
Continuing with the remaining client commands, RSET aborts the current mail transaction and resets the session state, clearing the sender, recipients, and any buffered data without closing the TCP connection.
The server replies 250 and the session returns to the state it was in after the initial EHLO.
NOOP performs no operation. It exists to keep an idle connection alive or to test that the server is still responsive. The server simply replies 250 and takes no further action.
VRFY asks the server to verify whether a given mailbox exists.
In practice, most servers disable this command or return a generic response as enabling it would allow an attacker to enumerate valid email addresses.
QUIT request an orderly closure of the SMTP session.
The server replies 221 and the TCP connection teardown follows.
Every server reply begins with a three-digit code.
The first digit indicates the class of the response.
Those beginning with two indicates a positive completion.
The requested action was successfully completed.

220 for service ready.
This is the opening greeting that the server sends immediately after the TCP connection is established before any client command is issued.
221 for closing channel.
The server sends this in response to quit, signaling that it is closing the connection.
250 for requested action okay.
This is the most common success response.
It acknowledges EHLO, mail from, receipt to, and the completion of the data transaction.
354 is start input.
This is the server's response to the data command.
